## 2. 구조와 데이터 흐름

```
date_utils.get_weekly_periods()   → (용도, 시작일, 종료일) 7개
        │
scraper_main.run_scraper()        → logs/scraper_YYYY-MM-DD.log 핸들러 재연결
        └ _scrape_all()           → CATEGORIES 4개 × 기간 7개 루프
             각 대상마다 새 browser context → 기간 드롭다운 → 카테고리 → 연령(40/50/60) → 조회
             → 25페이지 순회(페이지당 20건) → results/YYYY-MM-DD/카테고리_시작일_종료일.csv
        반환값: 실패한 파일명 리스트 (CLI는 실패 시 exit 1)

app.py (Streamlit)                → 버튼으로 run_scraper를 스레드 실행
                                    진행률은 **로그 파일 문자열을 파싱**해서 계산
                                    결과 화면은 **오늘 날짜 폴더만** 표시
```

- CSV 컬럼: `순위`(문자열로 저장됨), `검색어`, `수집기간`(`YYYY-MM-DD~YYYY-MM-DD`), 인코딩 `utf-8-sig`
- 1개 대상 수집에 약 55초 + 대기 3초 → 전체 약 28~30분
- 로컬은 headed(브라우저 창 표시), `GITHUB_ACTIONS=true`일 때만 headless

### 드롭다운 인덱스 규칙 (사이트 구조 의존, 가장 깨지기 쉬운 부분)
`page.locator("div.select")` 중 **화면에 보이는 것**만 모아서 인덱스로 접근합니다.
- 2: 기준(`일간`), 3~5: 시작 연/월/일, 6~8: 종료 연/월/일
- 값을 고르지 못하거나, 종료일 설정 후 다시 읽은 6개 값(`read_date_dropdowns`)이 기대값과 다르면 해당 대상만 실패 처리
- 카테고리는 `a.option:has-text(...)`를 가진 보이는 `div.select`를 찾아 클릭 (모바일용 숨김 요소 제외 목적)

### app.py ↔ scraper_main.py 결합 지점 (한쪽만 바꾸면 깨짐)
app.py는 로그 메시지의 다음 문자열에 의존합니다. 로그 문구를 바꿀 때 함께 수정해야 합니다.
- 대상 1건 종료: `"저장 성공"`, `"데이터 없음"`, `"에러 발생"`
- 현재 진행 중 표시: `"수집 시작"` (`]` 뒤 텍스트를 잘라 표시)
- 전체 종료: `"모든 데이터 수집 완료"`
- 또한 `CATEGORIES`, `output_filename`, `get_weekly_periods`를 import해서 파일명을 재계산합니다.

## 4. 알려진 문제 / 개선 후보 (우선순위 순)

### P0 — 실사이트 검증 (2026-10-19 완료)
1. 신규 7개 기간 로직을 실사이트에서 전체 실행했습니다. 확인된 내용은 다음과 같습니다.
   - 28개 CSV가 모두 생성됐고, 모두 500행이며, `수집기간` 컬럼이 파일명과 일치합니다.
   - 작년 연도(2025) 선택과 월이 걸치는 기간(10-27~11-02)에서도 `기간 설정 불일치` 오류가 없었습니다.
   - 같은 카테고리 안에서도 기간마다 순위가 달라서, 기간 설정이 실제로 반영된 것을 확인했습니다. 채소 +3주/+4주는 상위 5개가 같지만, 500개 중 같은 순위에 같은 검색어인 경우는 9개뿐이라 정상입니다.
   - **문제**: `채소_2026-10-12_2026-10-18.csv`에서 321~340위가 2번 들어갔고 361~380위가 빠졌습니다. 아래 P1-2가 실제로 재현된 사례입니다.
   - 검증 방법: 28개 파일마다 행 수, 순위 1~500 연속 여부, 검색어 중복, 기간 컬럼을 검사하고 기간 간 상위 결과를 비교했습니다. 다음에 테스트를 붙일 때 같은 기준을 쓰면 됩니다.

### P1 — 안정성
2. **고정 sleep 의존 (실제 발생, 2026-10-19 28개 중 1건)**: 조회 후 `time.sleep(4)`, 페이지를 넘긴 뒤 `time.sleep(1.5)`만 하고 목록이 바뀌었는지는 확인하지 않습니다. 그래서 페이지가 늦게 바뀌면 이전 페이지를 다시 읽고, 그 다음 페이지는 건너뜁니다. 개선 방향은 다음 클릭 전후로 첫 항목의 순위가 `(페이지-1)*20+1`이 될 때까지 `wait_for`하는 것입니다.
   - **진단 결과(2026-10-19)**: 같은 대상(채소 10-12~10-18)을 3회, 총 72번 페이지를 넘기며 계측했습니다. 순위 API(`getCategoryKeywordRank.naver`, POST `page=N&count=20`) 응답은 19~31ms, 화면 반영은 60~77ms였고, 1.5초 시점에 이전 페이지가 보인 경우는 0회였습니다. 서버 응답 78건도 모두 요청한 페이지의 순위가 맞았습니다. **평소에는 재현되지 않습니다.**
   - 결함 파일의 패턴(18페이지 자리에 17페이지가 한 번 더 들어가고, 다음 자리에 18페이지, 그 다음은 20페이지)은 **18페이지 응답이 한 번만 1.5초 넘게 늦어진 경우**와 맞아떨어집니다. 클릭이 누락됐다면 이후 순위가 모두 한 칸씩 밀려 최대 480위로 끝났을 것이고, 서버 오류 가능성은 위 검증으로 낮습니다. 즉 드물게 생기는 일시적 지연입니다.
   - 사이트가 요청마다 `page=N`을 명시하므로, `page.expect_response`로 해당 페이지 응답을 기다리는 방식도 가능합니다.
   - **수정 완료**: `wait_for_page()`가 목록 첫 순위가 `(N-1)*20+1`이 될 때까지 최대 15초 기다립니다(초과 시 해당 대상 실패). 요청 간격 1.5초는 봇 탐지 방지를 위해 그대로 유지했습니다.
   - 아직 남은 부분: 조회 버튼을 누른 뒤의 1페이지는 여전히 `time.sleep(4)`에 의존합니다. 이전 조회 결과도 1위부터 시작하기 때문에 순위만으로는 갱신 여부를 판별할 수 없습니다. 필요하면 `expect_response`로 보완해야 합니다.
3. **수집 결과 검증 (수정 완료)**: 결함 파일도 500행이라 "저장 성공"으로 기록됐고 종료 코드도 0이었습니다. 이제는 `validate_ranks()`가 저장 직전에 순위가 1부터 빠짐없이 이어지는지 검사하고, 어긋나면 파일을 저장하지 않고 `에러 발생 ... 순위 불연속`으로 실패 처리합니다. 재시도는 아직 없습니다(P1-4).
4. **재시도 없음**: 대상 1건 실패 시 그대로 실패. 대상 단위 1~2회 재시도 고려.
5. **동시 실행 방지 없음(app.py)**: `is_running`이 브라우저 세션 상태라서, 새로고침하거나 다른 탭에서 열면 수집 중인데도 버튼이 다시 활성화되어 두 번째 수집이 동시에 시작될 수 있음 → 락 파일 등 프로세스 수준 잠금 필요. 새로고침 시 진행률도 사라짐.
6. **CI와 로컬 버전 불일치**: `requirements.txt`가 버전 미고정이고 CI는 Python 3.10, 로컬은 3.14. pandas 3.x는 Python 3.11+ 전용이므로 CI에서는 2.x가 설치됨. 버전 고정 또는 CI Python 상향 검토.

## 5. 작업 시 규칙 / 관례

- 실행은 반드시 `.venv`의 Python으로: Windows `.venv\Scripts\python.exe`, Mac `.venv/bin/python`
- 기간 확인: `.venv\Scripts\python.exe date_utils.py` (Git Bash에서는 한글이 깨져 보일 수 있음, PowerShell 권장)
- 커밋 메시지: 한국어 Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`) + 본문에 변경 이유를 `-` 목록으로
- 사이트 셀렉터를 바꾸는 작업은 로컬 headed 모드로 브라우저를 직접 보며 검증
- 수집은 네이버 사이트에 부하를 주므로 대상 간 대기(현재 3초)는 줄이지 않기
- **Windows 스마트 앱 컨트롤(SAC) 일시 차단**: 이 PC는 SAC가 켜져 있습니다(레지스트리 `VerifiedAndReputablePolicyState=1`). 2026-10-19 10:12:58에 `.bat`로 대시보드를 실행했을 때 서명되지 않은 numpy DLL(`numpy\random\mtrand.cp314-win_amd64.pyd`)이 차단되어 `ImportError: DLL load failed ... 애플리케이션 제어 정책에서 이 파일을 차단했습니다`가 발생했습니다(CodeIntegrity 이벤트 3077). 같은 파일이 5분 뒤부터는 정상 로드됐고, 10-08 이후 차단 기록은 이 1건뿐입니다. 일시적인 평판 확인 실패로 추정됩니다. 재발하면 브라우저 새로고침(F5) 또는 `.bat` 재실행으로 대부분 해결됩니다. SAC를 끄는 것은 보안 설정이므로 사용자가 판단할 사항입니다.
